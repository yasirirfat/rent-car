## Follow-up: token consistency pass on screens not fully reworked

Because `AppColor` is global, screens that were *not* part of the redesign
(`saved_screen`, `bookings_screen`, `intro_screen`, `widgets/header.dart`,
`widgets/search_bar.dart`, `widgets/chips.dart`) inherited the new palette but
kept ad-hoc styling habits. Audited and normalised:

### Two new token families added to `AppColor`
1. **Translucent surface veils** — small controls (chips, icon buttons,
   inputs) sit *over the background* rather than on another card, so a
   translucent fill letting the grid read faintly through is intentional and
   reads as glassy. The problem was 5 different opacities (0.5/0.55/0.6/0.7/
   0.85) with no system. Now three named steps:
   - `surfaceVeil` (0.55) — resting control
   - `surfaceVeilStrong` (0.72) — hovered / active elevation
   - `surfaceVeilMax` (0.85) — focused input
   - `accentVeil(accent, {alpha})` — tinted fill for a *selected* control
   **Important:** do NOT "fix" these by making them opaque. An earlier attempt
   to make the bookings date chip opaque was a regression in the opposite
   direction; the token approach preserves the glass effect while standardising
   it.
2. **Corner radius scale** — `radiusChip 10`, `radiusControl 14`,
   `radiusCard 18`, `radiusPanel 24`. Radius grows with surface area, so small
   chips stay tight and large feature panels stay generous. Replaced all
   ad-hoc 22/24/26 panel radii with `radiusPanel`.

### Header avatar — real bug avoided
`header.dart` had a hardcoded `CircleAvatar(radius: 20)`. Replaced with a
`ClipOval` + `Stack` where the **monogram (`state.profile.initials`) is an
underlay** and the photo paints on top. Reason: relying on `Image.asset`'s
`errorBuilder` alone means a missing/undecodable photo leaves a *blank circle*
until the error resolves. Underlay guarantees a filled avatar always.

**Test gotcha:** in `flutter_test`, `Image.asset` for a missing asset does
**not** fire `errorBuilder` — it stays an `Image` widget with no decoded frame,
silently. So a test can never assert the errorBuilder path. The underlay
approach is what makes the initials assertable. Verified by probe: `Image`
widget count = 1, `ClipOval` = 1, no exception.

### Tests: 40 -> 42
Added group `Header avatar and bookings surfaces`:
- header renders `YA` (initials of default profile "Yasir Ahmed") + one ClipOval
- bookings renders its two segment labels (`Active & Upcoming`, `History`) with
  no overflow exception

**Test-authoring mistakes made and corrected:**
- Asserted `YS` for initials; `UserProfile.initials` takes *first + last* word
  letters, so "Yasir Ahmed" -> `YA`.
- Asserted `find.text('All rides')` on the bookings screen — the segment labels
  are actually `Active & Upcoming` / `History`. Always grep the real label
  strings before asserting them.
- Two Edit calls reported success but had not matched the intended block (a
  stale-content race after an earlier edit). **Lesson: after a batch of edits to

## LIGHT THEME CONVERSION (later the same day) — supersedes the dark palette

The user then asked for a **clean, simple, modern light theme** inspired by a
reference design (Porsche 718 Cayman rental app): white cards on a near-white

The dark neon palette described above is now historical — do not reintroduce it.

### Palette (`lib/core/app_color.dart` — rewritten)
`canvas #F3F5F9`, `surface #FFFFFF`, `surfaceHigh #F5F7FA`,
`stroke #E4E8EF`, `strokeStrong #CDD5E0`,
text ramp `#111827 / #5A6472 / #8A93A2`,
`primary #2F6BE4` (blue = action), `secondary #0FA396`, `amber #F0A82E`,
`danger #E5484D`, `success #19A974`, and a new `scrim #0B1220` (modal barrier,

**Every token NAME was preserved** so the other ~30 files kept compiling. The
gradient tokens (`brandGradient`, `appBackground`, `glassFill`, …) still exist
but each resolves to a *flat* colour with both stops identical. Two new tokens
were added: `scrim` and the radius scale.

### THE `obsidian` TRAP — read this before touching colours
`obsidian` used to be near-black. Many widgets used it as **foreground on a
bright accent fill** (e.g. text on a blue button). Flipping it to near-white
silently makes all that text invisible. Sites like this were converted to
`Colors.white`. Sites where it acted as a **dark ink** (modal barriers, badge
borders, chart shadow lerp) were converted to the new `AppColor.scrim`, which is
always dark regardless of theme. If you add a light surface and text vanishes,
you have hit this pattern.

### No gradients — enforced
Removed gradients from: `CarCardPainter`, `_GridCardPainter`, `HeroBannerPainter`
(the big one — previously a violet gradient with a radial glow, speed streaks and
a perspective grid), `GlassCardPainter`, `AuroraPainter`, `SpeedometerPainter`
(arc, power band, needle, hub), `ProgressRing`/`StatBar`, `ComparisonChart`,
`_NavBarPainter`, `_GalleryBackdropPainter`, `chips.dart` (selected chip), the
`_SheetDivider`s (fading hairlines) and the intro `_brandShader`.
Verified with `grep -rn "Gradient" lib/ | grep -v app_color.dart` → empty.
A test now walks every `Container` decoration in a card and asserts no gradient.

### Car image consistency (§ explicit requirement)
`CarCard.imageBoxWidth/Height = 240 x 104`, used by BOTH the list card and the
grid card, with `BoxFit.contain` and a `LayoutBuilder` for the error fallback.
A path is supplied to the image box through a small `CarImageScope`
`InheritedWidget` so the box doesn't need the model threaded through.
Test measures the box across 6 different cars and asserts pixel-identical sizes.
